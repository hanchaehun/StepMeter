# W2 벤치마크 도구와 전환 과업

기준: 개발계획서 8장, ADR 0003·0007·0008. 이 문서는 구현 현황이며 팀 범위 변경 결정이 아니다.

## 재현

루트의 Python 3.12 가상환경·npm 의존성·Chromium·수집 번들을 준비한다(infra/README.md).

```sh
npm run build:collect
python -m benchmark.verify_conversion
python -m unittest tests.test_benchmark_eval -v
```

브라우저 실행 환경에 따라 `PLAYWRIGHT_BROWSERS_PATH="$PWD/.venv/ms-playwright"`를 설정한다.
검증기는 임시 loopback 서버를 직접 시작하고 종료한다. 외부 서버·API·결제는 사용하지 않는다.
수동 조작: `python -m http.server 8770 --bind 127.0.0.1 --directory benchmark/fixtures/conversion` 후 http://127.0.0.1:8770 에 접속한다.

## 과업과 성공 조건

| 과업 | 경로 | 성공 조건 |
|---|---|---|
| 무료 가입 | 쿠키 선택 → 이메일·8자 이상 비밀번호 → 가입 | `#result`가 `데모 가입 완료` |
| 구독 선택 | 쿠키 선택 → 열린 Shadow DOM의 Pro → 같은 출처 iframe의 확인 | iframe `#confirmation`에 `데모 구독 확인 완료` |

로그인·테스트 계정 저장 기능이 아니다(ADR 0004). 데이터는 페이지 메모리에만 있다.
쿠키 모달은 사용자 클릭으로만 닫는다. 정상 화면과 결함 화면을 새 페이지로 분리해 상태 누적을 막는다.

## 결함 설정

`mutations/conversion/*.yaml`은 YAML 1.2의 JSON 부분집합이다. `mutate.py`가 Playwright 페이지에 적용한다.
원본 파일은 바꾸지 않는다. 셀렉터가 정확히 하나를 가리키지 않으면 실패한다.

| 변이 | 실수 패턴 | 확인 근거 |
|---|---|---|
| small / R01 | 아이콘 툴바 크기 유틸리티 오용 | 인접 16×16 버튼 두 개, 중심 간격 24 미만 → WCAG 2.5.8 간격 예외 불충족 |
| contrast / R02 | 흰 배경에 밝은 글자 클래스 | #eee / #fff, 약 1.16:1; axe color-contrast 확인 |
| inert / R03 | submit 핸들러 연결 누락 | 유효한 입력 후 클릭해도 완료 문구 없음 |
| overlay / R04 | 로딩 레이어 제거 누락 | 중심점 hit test가 오버레이, snapshot.occluded=true |
| below-fold / R06 | 잘못 붙인 전체 화면 여백 | 1280×800 초기 화면 밖, 첫 화면 노출 false와 필요한 스크롤 값 |
| unnamed / R10 | 아이콘 교체 중 텍스트·이름 누락 | 빈 이름 버튼, axe button-name 확인 |

정상 1 + 변이 6을 실행해 DOM 계산값·스냅샷·axe 원시 결과·PNG를 `evidence/conversion/`에 보존한다(git 제외).
정상 화면의 모달 처리 직후 수동으로 정한 요소 5개 목록과 수집 결과를 비교하며 Shadow DOM/iframe context와 프레임 좌표를 확인한다.
이것은 합성 화면 검증이다. SPA 3개 스트레스 테스트 통과나 LLM 에이전트 완주율을 뜻하지 않는다.
다른 출처 iframe·닫힌 Shadow DOM·가상 스크롤은 이 화면에 포함하지 않았다.

## 정답과 평가

`labels/conversion.json`은 렌더링 확인 후 생성한 **PM 검토 대기** 정답이다.
PM은 실행 증거와 과업·규칙 대응을 검토한 뒤 review_status를 approved로 바꾼다.
규칙 작성자가 만든 예측을 정답으로 복사해서는 안 된다.

```sh
python -m benchmark.eval --labels benchmark/labels/conversion.json --predictions /tmp/predictions.json --output /tmp/evaluation.json
```

예측 형식: `{"split":"development","cases":{"baseline":[],"small":[{"rule":"R01","target":"#signup"}],...}}`.
모든 case를 명시하고 미탐지 케이스도 빈 배열로 넣는다. 키는 case·rule·안정적 target 세 개로 매칭한다.
같은 키의 중복 검출은 한 번으로 센다. 정상 화면의 검출은 FP다. 미검토 정답·누락 케이스·홀드아웃 입력은 거절한다.
정밀도·재현율·F1을 micro와 규칙별로 출력하며, 분모가 0인 값은 null이다.
이 형식은 벤치마크 내부 교환 형식이며 공용 API를 바꾸지 않는다. 실제 검출 결과의 target 정규화는 평가자가 수행해야 한다.
검증기는 정답과 같은 결과를 예측으로 만들어 성능을 주장하지 않는다.

## 남은 W2 완료 조건

- 기존 개발 앱 4개의 실행·정상 동적 상태 승인 및 앱당 6종 변이. 현재 보조 fixture를 앱 개수에 포함하지 않는다.
- 홀드아웃 2개의 준비는 제한된 저장소에서만 수행한다. 이번 도구는 홀드아웃을 읽거나 평가하지 않는다.
- PM 정답 교차 검토, LLM·프롬프트 담당의 같은 경로 LLM/axe 1차 비교.
- 실제 개발 앱 결과 생성 후 월요일 평가 CI 연결. 현재 CI는 합성 fixture 검증과 증거 저장만 수행한다.
- API 실행 서버·전체 워커 진입점이 main에 없어 실제 API→큐→DB→리포트 스테이징 검증은 미완료다.
