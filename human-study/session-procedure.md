# 사람 실험 세션 진행 절차

참가자 한 명의 세션을 처음부터 끝까지 어떤 순서로 진행하고 무엇을 말하는지 적은 문서다. 진행자마다 설명이 달라지면 측정값도 흔들리므로, 말하는 문장은 아래 대본을 그대로 읽는다.

- **담당:** 대시보드 UI (세션 운영)
- **상태:** 안. 파일럿 3명을 마친 뒤 확정한다. 아래 "파일럿에서 확인할 것" 참고.
- **함께 보는 문서:** [동의서](consent-form.md), [6페이지와 과업 문장](pages.md), 수집 스크립트 사용법(#33의 `human-study/README.md`)

## 세션 전 (그날 한 번)

| 할 것 | 기준 |
|---|---|
| 진행자 PC 화면 | 논리 해상도 세로 950px 이상. 모자라면 디스플레이 배율을 100%로 낮춘다. 창 1280×800이 다 보여야 첫 화면 판정(R06)이 맞다 |
| 입력 장치 | 진행자 PC에 마우스를 연결한다. 모든 참가자가 마우스를 쓴다(`--device mouse`) |
| 벤치마크 서버 | 아래 "페이지별 주소"의 서버 5개를 띄우고, 브라우저로 한 번씩 열어 본다 |
| 수집 스크립트 | `infra/README.md` "W1 실행 환경"대로 준비한다. Playwright Chromium을 띄운다 |
| 종이 | 동의서(1절 담당자·연락처를 채운 인쇄본), 참가자 코드 기록용 메모 |

### 페이지별 주소

서버는 `benchmark/serve_variants.py`로 띄운다. 포트와 주소는 `benchmark/variants.json`에 있고 아래 표와 같다.

| # | `page_id` | 서버 | 시작 주소 |
|---|---|---|---|
| 1 | `sb-admin-2/register/baseline` | 기준선 | `http://127.0.0.1:8766/register.html` |
| 2 | `material-kit-react/products/baseline` | 기준선 | `http://127.0.0.1:8767/products` |
| 3 | `material-kit-react/sign-in/baseline` | 기준선 | `http://127.0.0.1:8767/sign-in` |
| 4 | `sb-admin-2/login/small` | 기준선 + `small.patch` | `http://127.0.0.1:8791/login.html` |
| 5 | `shadcn-admin/tasks/contrast` | 기준선 + `contrast.patch` 빌드 | `http://127.0.0.1:8782/tasks` |
| 6 | `shadcn-admin/users/below-fold` | 기준선 + `below-fold.patch` 빌드 | `http://127.0.0.1:8785/users` |

저장소 루트에서 아래 순서로 실행한다.

```sh
python -m benchmark.serve_variants build   # 처음 한 번. 패치 해시가 같으면 다시 빌드하지 않는다
python -m benchmark.serve_variants check   # 결함판 4·5·6번은 결함 발현(4번은 R01, #41에서 링크 간격 조정), 기준선은 깨끗한지 확인 (실패하면 종료 코드 1)
python -m benchmark.serve_variants serve   # 서버 5개를 띄우고 page_id별 주소 표를 보여 준다
python -m benchmark.serve_variants stop    # 그날 세션이 끝나면 정리
```

빌드 기록(`*.manifest.json`: 앱·커밋·패치 sha256·빌드 시각)과 serve 기록(`serve-history.jsonl`)은 `benchmark/apps/variants/`에 남는다(git 제외).

## 진행 순서

### 1. 참가 조건 확인 (과업 설명보다 먼저)

> "시작하기 전에 하나만 여쭤볼게요. 관리자 대시보드나 로그인 화면 같은 웹 화면 몇 개를 쓰실 텐데, 혹시 SB Admin, Material Kit, shadcn admin 같은 관리자 템플릿 화면을 전에 써 보신 적 있으세요?"

- "있다"면 그 자리에서 설명하고 데이터를 받지 않는다: "이번 연구는 처음 보시는 분의 기록이 필요해서요. 시간 내 주셔서 감사합니다."
- 과업 설명을 들은 뒤에는 "본 적 있다"고 말하기 어려워지므로 이 질문을 맨 먼저 한다(동의서 운영 메모).

### 2. 동의서

1. 동의서를 건네고 읽을 시간을 준다. 3·4절(기록하는 것, 기록하지 않는 것)을 짚어 준다: "입력하신 글자는 저장하지 않고, 키를 누른 시각만 남습니다."
2. 질문을 받고 서명을 받는다.
3. 참가자 코드를 정한다. `P01`부터 순서대로 쓴다. 동의서에는 코드를 적지만, 코드와 사람을 잇는 표는 만들지 않는다.

### 3. 공통 안내

> "이제 웹 페이지 6개에서 간단한 일을 하나씩 해 주시면 됩니다. 빨리 하거나 잘할 필요는 없어요. 평소에 하시던 대로 하시면 됩니다. 중간에 막히면 끝내지 못하셔도 괜찮습니다. 입력 칸에는 제가 알려 드리는 가짜 값만 넣어 주세요."

> "평소에 컴퓨터를 하루 몇 시간쯤 쓰세요? 대략이면 됩니다."

답한 시간을 `--hours`에 적는다.

### 4. 페이지 6개

순서는 아래로 고정한다. 비슷한 로그인 과업인 3번과 4번 사이에 다른 과업 두 개를 둬서 학습 효과를 줄였다. 결함 페이지가 어디인지는 말하지 않는다.

| 차례 | 1 | 2 | 3 | 4 | 5 | 6 |
|---|---|---|---|---|---|---|
| 과업 # | 1 | 3 | 5 | 2 | 4 | 6 |

페이지마다 다음을 반복한다.

1. 수집 스크립트를 실행한다.
   ```sh
   python human-study/session.py --participant P01 --page-id <page_id> --url <시작 주소> --device mouse --hours <시간>
   ```
2. Chromium 창이 뜨고 페이지가 다 보이면, `pages.md`의 과업 문장을 **그대로** 읽는다. 2번 과업은 문장 앞에 "이 페이지는 데모라 정렬이나 필터를 바꿔도 목록은 바뀌지 않습니다"를 먼저 읽는다.
3. 참가자가 하는 동안 돕지 않는다. 질문을 받으면 과업 문장만 다시 읽어 준다. 그 밖에는 "편하신 대로 해 주세요"라고만 답한다.
4. `pages.md`의 "끝난 것으로 보는 시점"이 화면에 나타나면 터미널에서 **Enter**를 누르고, "과업을 끝냈나요?"에 `y`로 답한다.
5. **3분**이 지나도 끝나지 않으면 "여기까지 하셔도 됩니다"라고 말하고 Enter를 누른 뒤 `N`으로 답한다. 참가자가 그만두겠다고 하면 같은 방법으로 처리한다.

### 5. 끝

> "끝났습니다. 참가자 코드는 P01입니다. 나중에 기록을 지우고 싶으시면 이 코드를 알려 주시면 됩니다."

코드를 종이에 적어 드린다(동의서 6절).

## 세션 뒤

- 저장된 파일 6개(페이지당 1개)가 있는지 확인한다. `*.invalid.json`이 생겼으면 지우지 말고 오류 내용을 수집 스크립트 담당에게 알린다.
- 저장 위치는 `data/human/`이다. git 제외 폴더이며 **커밋하지 않는다.**
- 세션이 끝나면 `benchmark/apps/variants/`의 manifest(`<앱>/<변이>.manifest.json`)와 `serve-history.jsonl`을 참가자 데이터와 같은 비공개 폴더에 복사한다. 참가자가 어떤 빌드를 봤는지 증명하는 기록이다.
- 서명한 동의서는 데이터와 분리해 보관한다. 사진을 찍거나 스캔해 올리지 않는다.
- API가 생기면 `upload.py`로 올린다.

### 삭제 요청

참가자가 코드를 알려 주면 그 코드의 파일을 모두 지우고(올렸다면 서버 데이터도), 지웠다고 답한다. 이미 여러 사람을 합쳐 계산한 결과는 되돌리지 않는다(동의서 6절).
