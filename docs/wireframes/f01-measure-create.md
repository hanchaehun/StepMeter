# F01 측정 생성 화면 레이아웃 명세 (검토안)

측정 생성 화면의 영역 구조, 입력 필드, 상태 전환을 정한다. 시각 목업은 같은 폴더의 [`f01-measure-create.html`](f01-measure-create.html)이며 브라우저로 열어 본다. 이 문서가 값과 규칙의 기준이고, 목업은 그 배치를 보여주는 참고물이다.

- **범위:** 측정 생성 화면 하나. 측정 진행(F02), 비교(F07), 측정 이력(F11)은 별도 문서로 다룬다.
- **근거:** 서비스 기획서 **5장 기능 정의 F01 행**(입력 필드와 반복 횟수), **6.1 화면 목록 측정 생성 행**(예시 제공, 측정에 걸릴 시간) / 개발계획서 3장·13장(역할 경계)·14장(W1 완료 기준)
- **아직 정해지지 않은 것:** 디자인 시스템(리포트 UI 담당)과 `apps/api/openapi.yaml`. 둘이 확정되면 이 문서의 색·간격·필드명을 거기에 맞춘다.

## 영역 구조

데스크톱 1280×800 기준. 본문은 입력 열(가변)과 요약 열(320px) 2열이다.

```
┌─ 앱 헤더 (높이 56) ──────────────────────────────────────────┐
│ StepMeter    새 측정 · 측정 이력 · 비교      오늘 남은 7/10회 │
├─ 본문 (padding 24, gap 32) ──────────────┬───────────────────┤
│ 새 측정 만들기                            │ 측정 예상          │
│ 측정할 주소   [__________________]        │  약 4분 30초       │
│ 과업          [__________________]        │  반복 3회 기준     │
│               (예시 칩 3개)               │  · 데스크톱        │
│ 성공 조건     [__________________] 선택   │ ─────────────      │
│ 테스트 계정   [______] [______] M3 이후   │ · 3회 중앙값 사용  │
│ 화면 크기     (•)데스크톱 ( )모바일       │ · 사이트 속도 영향 │
│ ▸ 고급 설정 — 측정 신뢰도 높이기          │ · 진행 중 취소 가능│
│ [측정 시작] [취소]  반복 3회 (기본)       │                   │
└──────────────────────────────────────────┴───────────────────┘
```

좁은 화면에서는 한 열로 쌓고, 요약 열을 측정 시작 버튼 바로 위로 옮긴다. 헤더의 남은 횟수는 버튼 아래 문구로 내린다.

## 입력 필드

### 필드 목록의 근거

서비스 기획서 두 곳을 합쳐야 전체가 나온다. 5장에는 테스트 계정이 있고 6.1에는 없다. 6.1에는 예시 제공과 측정에 걸릴 시간이 있고 5장에는 없다.

> **5장 F01 행:** URL, 과업, 성공 조건(선택), 테스트 계정(선택), 화면 크기 입력. 반복 횟수는 기본 3회, 고급 설정에서 5회
>
> **6.1 측정 생성 행:** URL, 과업 입력(예시 제공), 성공 조건, 화면 크기, 반복 횟수, 측정에 걸릴 시간

| 이 문서의 필드 | 5장 F01 | 6.1 화면 목록 |
|---|---|---|
| 측정할 주소 | URL | URL |
| 과업 | 과업 | 과업 입력(예시 제공) |
| 성공 조건 (선택) | 성공 조건(선택) | 성공 조건 |
| 테스트 계정 (선택) | 테스트 계정(선택) | — |
| 화면 크기 | 화면 크기 | 화면 크기 |
| 반복 횟수 | 기본 3회, 고급 설정에서 5회 | 반복 횟수 |
| (요약 패널) 측정 예상 | — | 측정에 걸릴 시간 |

### 기획서에 없고 이 문서에서 정한 것

리뷰할 때 근거가 있는 것과 없는 것을 구분해야 하므로 따로 적는다.

| 항목 | 출처 |
|---|---|
| 화면 크기 수치 (데스크톱 1280×800 / 모바일 390×844) | 기획서에 수치 없음. 대시보드 UI 작업 메모 |
| 예상 소요 시간을 데스크톱만 표시 | 리포트 숫자 표기 원칙(보정되지 않은 값을 보정이라 쓰지 않는다)에서 끌어왔다 |
| 5회에 예상 **비용**을 함께 표시 | 기획서는 시간만 말한다. 비용 표시는 이 문서에서 더했다 |
| 검증 오류 문구, 상태 전환, `401`·`429` 화면 | 기획서에 화면 수준 정의가 없다. F17 접근 제어 요구에서 구성했다 |
| 칩 라벨과 입력 문장을 분리 | 기획서 근거 없음. 타겟 크기 44px를 지키면서 한 줄을 유지하려는 이 문서의 설계 |

위 5건 중 반대 의견이 있으면 이 문서를 고친다. 기획서에 근거가 있는 항목(위 대조표)을 바꾸려면 기획서를 먼저 고쳐야 한다.

### 필드별 규칙

| 필드 | 필수 | 형식 | 검증 | 비고 |
|---|---|---|---|---|
| 측정할 주소 | 필수 | 문자열 | `http://` 또는 `https://`로 시작 | 포커스 이탈과 제출 시점에 검사 |
| 과업 | 필수 | 문자열 1줄 이상 | 공백만이면 거절 | 예시 칩 3개 제공 |
| 성공 조건 | 선택 | 문자열 | 없음 | 비우면 에이전트가 과업 문장으로 판단 |
| 테스트 계정 | **M3 이후(비활성)** | 아이디·비밀번호 | 한쪽만 채우면 거절 | 동결된 `openapi.yaml`의 `TaskCreate`가 아직 받지 않는다. 받기 시작하면 리포트·스크린샷에 남기지 않음 |
| 화면 크기 | 필수 | `desktop` \| `mobile` | — | 데스크톱 1280×800 / 모바일 390×844, 기본 데스크톱 |
| 반복 횟수 | 필수 | `3` \| `5` | — | 기본 3회. 5회는 고급 설정 안 |

과업 예시 칩은 벤치마크 앱 종류에 맞춰 세 가지를 둔다: 가입 완료형, 커머스 결제형, 비교·선택형. 칩이 입력값을 덮어쓰므로 이미 입력된 내용이 있으면 덮어쓸지 묻는다.

**칩 라벨과 넣는 문장은 다르다.** 라벨은 짧게 쓰고(타겟 44px를 지키면서 한 줄에 셋을 넣기 위해), 누르면 완전한 문장이 들어간다.

| 칩 라벨 | 입력칸에 들어가는 문장 |
|---|---|
| 계정 만들기 | 무료 계정을 만든다 |
| 장바구니 담기 | 장바구니에 상품을 담고 결제까지 간다 |
| 요금제 고르기 | 가장 싼 요금제를 찾아 신청한다 |

라벨만 짧게 하면 타겟 크기를 지키면서도 "과업은 한 문장으로 쓴다"는 유도 효과가 남는다. 칩 아래에 "누르면 완전한 문장이 들어간다"를 한 줄 적어 라벨이 곧 입력값이 아님을 알린다. 실제 문장은 W2에 벤치마크 페이지 6개가 확정되면 그에 맞춰 바꾼다.

### 오류 표시

오류는 색만으로 알리지 않는다. 테두리 색 + 두께 2px + `▲` 기호 + 문장을 함께 쓴다.

| 상황 | 문구 |
|---|---|
| 주소 형식 오류 | 주소는 https:// 또는 http:// 로 시작해야 한다. |
| 과업 비어 있음 | 과업을 한 문장으로 적는다. 아래 예시를 눌러 넣을 수 있다. |
| 계정 한쪽만 입력 | 아이디와 비밀번호를 함께 넣는다. 둘 다 비우면 계정 없이 측정한다. |

문구는 무엇을 해야 하는지로 쓰고 입력값을 되풀이하지 않는다. 오류 문구는 해당 입력칸과 `aria-describedby`로 잇고, 제출 실패 시 첫 오류 칸으로 포커스를 옮긴다.

## 예상 시간과 비용

| 반복 | 표시 위치 | 표시 내용 |
|---|---|---|
| 3회 (기본) | 요약 열, 버튼 옆 | 예상 소요 시간만 |
| 5회 | 고급 설정 안, 요약 열, 버튼 옆 | 예상 소요 시간 + 예상 비용, 각각 3회 대비 증가분 |

- 숫자 옆에는 항상 기준을 쓴다: "약 4분 30초 (반복 3회 기준 · 데스크톱)".
- 증가분은 색으로만 구분하지 않고 "(3회 대비 +3분)" 문구로 쓴다.
- **예상 소요 시간은 데스크톱에서만 표시한다.** 모바일을 고르면 이 영역을 숨기고 이유를 한 줄로 쓴다.
- 목업의 숫자(4분 30초, $0.30 등)는 자리를 보여주는 예시값이다. 실제 값은 측정 지표·규칙 담당의 추정식이 나오면 맞춘다.
- 계산 주체는 시간과 비용을 나눈다. 시간은 화면이 추정하고 비용은 서버 응답을 쓴다(아래 요청 목록 참조). 비용만 로딩·실패 상태를 가지므로 요약 열에서 두 값의 표시 규칙이 다르다.

| 상태 | 예상 소요 시간 | 예상 비용 |
|---|---|---|
| 입력 부족 | `—` + "주소와 과업을 넣으면 계산한다" | 표시하지 않음 |
| 계산됨 | 즉시 표시 | 서버 응답값 표시 |
| 비용 조회 실패 | 그대로 표시 | "비용을 가져오지 못했다" + 다시 시도 |
| 모바일 선택 | 아래 문구로 대체 | 서버 응답값 표시 |

비용 조회가 실패해도 측정 시작은 막지 않는다. 비용은 참고값이고 측정 자체를 가로막을 이유가 아니다. 시간은 화면이 추정하므로 서버 응답과 무관하게 항상 나온다.

**모바일을 고르면 시간 자리를 비우지 않고 이유를 남긴다.** 숫자가 말없이 사라지면 사용자는 고장으로 본다.

> 모바일은 시간 추정을 제공하지 않습니다. 시간은 데스크톱 기준으로만 계산합니다.

비용은 화면 크기와 무관하므로 모바일에서도 그대로 표시한다. 네 상태 모두 목업 7번 프레임에 그려 뒀다.

## 상태 전환

| 상태 | 조건 | 화면 |
|---|---|---|
| 입력 전 | 기본 | 빈 폼, 예상 시간 영역은 `—` |
| 검증 오류 | 제출 시 필수값 누락·형식 오류 | 해당 칸에 오류 표시, 버튼 옆에 남은 항목 수 |
| 전송 중 | 제출 후 응답 대기 | 측정 시작 버튼을 진행 표시로 바꾸고 입력 잠금 |
| 성공 | 측정 생성됨 | 측정 진행 화면(F02)으로 이동 |
| 초대 코드 필요 | 응답 `401` | 초대 코드 입력 화면 |
| 상한 초과 | 응답 `429` | 상한 초과 안내 + 측정 이력 보기 + 재생만 다시 하기 |

### 접근 제어 (F17)

- 모든 요청에 `X-Access-Code` 헤더를 넣는다. 코드를 화면 코드에 하드코딩하지 않는다.
- `401`이면 초대 코드 입력 화면으로 보낸다. 코드가 틀리면 같은 화면에서 오류를 띄우고 남은 시도 횟수는 노출하지 않는다.
- `429`이면 "오늘 측정 상한(기본 10회) 초과"를 알린다. 막다른 길로 끝내지 않고 측정 이력과 재생만 다시 하기를 함께 제시한다.
- **재생만 하는 측정(`replay_only`)은 상한에 세지 않는다.** 헤더의 남은 횟수가 0일 때도 재생은 쓸 수 있다.

## 플랫폼 백엔드에 요청할 것

`apps/api/openapi.yaml`은 CODEOWNERS로 보호되는 공용 스키마라 이 문서에서 고치지 않는다. 이 화면이 필요한 것을 정리해 담당자(한채훈·오준호)에게 요청한다.

| 필요한 것 | 왜 |
|---|---|
| 측정 생성 요청 본문 필드명 | 위 입력 필드 6개를 어떤 이름으로 보내는지 확정이 필요하다 |
| `replay_only` 플래그 위치 | 상한 카운트 제외 여부를 화면에서 판단해야 한다 |
| `429` 응답의 상한·초기화 시각 | 안내 문구에 상한값과 초기화 시점을 쓰려면 응답에 있어야 한다 |
| 남은 측정 횟수 조회 | 헤더의 "오늘 남은 7/10회"를 그릴 출처가 필요하다 |
| 예상 소요 시간·비용 계산 주체 | 아래 제안대로 나눠도 되는지 확인이 필요하다. 요약 열의 상태 구조가 갈린다 |

확정 전까지는 목 JSON으로 개발한다. API 타입은 확정 후 `openapi-typescript`로 생성하고 손으로 만들지 않는다.

### 예상 소요 시간·비용 계산 주체 (제안)

항목에 따라 계산 주체를 나눈다.

| 항목 | 계산 주체 | 근거 |
|---|---|---|
| 예상 소요 시간 | **화면 추정** | 실제 시간은 측정 대상 사이트의 응답 속도에 달려 있어 서버도 정확히 알 수 없다. 화면이 `회당 평균 시간 × 반복 횟수 + 고정 오버헤드`로 계산하면 반복 횟수를 바꿀 때 즉시 반영된다 |
| 예상 비용 | **서버 응답** | LLM 호출 토큰 수에 달린 값이라 화면에는 추정할 근거가 없다. 예산 상한·알림도 플랫폼 백엔드 소유다(13.1) |

여기서 **화면 추정**은 서버에 묻지 않고 브라우저가 가진 입력값과 상수만으로 프론트엔드가 직접 계산하는 방식이다. **서버 응답**은 API를 호출해 받은 숫자를 그대로 표시하는 방식이다.

이렇게 나누면 요약 열에서 **비용만 로딩·실패 상태를 갖고** 시간은 항상 즉시 표시된다. 둘 다 서버 응답으로 가면 과업을 타이핑하는 중에 요청이 쏟아지지 않도록 디바운스가 필요하고, 패널 전체가 로딩 상태를 가져야 한다.

요청할 것:

1. 예상 비용을 어디서 받는지 — 측정 생성 전 별도 조회인지, 생성 응답에 포함인지
2. 예상 시간의 회당 평균 시간과 고정 오버헤드 상수를 어디서 받는지 — 화면에 상수를 박으면 바꿀 때 재배포가 필요하므로, 서버 설정값으로 내려줄 수 있는지
3. 위 분리가 맞지 않다면 어느 쪽으로 합칠지

## 자체 UX 기준 적용

StepMeter는 남의 UX를 지적하는 도구라 이 화면이 먼저 기준을 지켜야 한다. W4부터 StepMeter로 자기 측정할 때 아래가 0건이어야 한다.

| 기준 | 목업 적용 |
|---|---|
| 텍스트 대비 4.5:1 이상 | 본문 `#0a0a0a` 19.80:1, 보조 설명 `#525252` 7.81:1, 오류 `#b91c1c` 6.47:1 |
| 그래픽 요소 3:1 이상 | 조작 요소 경계 `#737373` — 흰 배경 4.74:1, `#f5f5f5` 위 4.35:1 |
| 타겟 24×24 이상 (권장 44×44) | 버튼·입력칸·내비·과업 예시 칩 모두 44px. 권장치 미달 요소 없음 |
| 이름 없는 요소 0건 | 아이콘만 있는 메뉴 버튼에 `aria-label` |
| 색만으로 의미 전달 금지 | 오류는 `▲`와 문장, 선택 상태는 "· 선택됨", 비용 증가는 "(3회 대비 +$0.12)" |

### 경계색을 두 가지로 나눈 이유

| 토큰 | 값 | 흰 배경 대비 | 쓰는 곳 |
|---|---|---|---|
| `--control-border` | `#737373` | 4.74:1 | 입력칸, 버튼, 라디오 카드, 과업 예시 칩, 고급 설정 — **조작할 수 있는 모든 요소** |
| `--border` | `#d4d4d4` | 1.48:1 | 헤더 밑줄, 카드 테두리, `hr` — **영역만 나누는 장식선** |

조작 요소의 경계는 그 요소가 어디까지인지 알려 주므로 3:1을 지켜야 한다. 영역을 나누기만 하는 선은 WCAG 1.4.11의 적용 대상이 아니다(순수 장식 제외). 이 구분을 지키지 않고 밝은 회색을 입력칸에 쓰면 3:1을 못 넘긴다. 처음 목업에서 입력 테두리로 쓴 `#a3a3a3`이 2.52:1로 미달이어서 `#737373`으로 바꿨다.

대비값은 WCAG 2.x 상대 휘도 공식으로 계산했다. 디자인 시스템이 확정되면 그 색으로 다시 계산한다.

## 결정한 사항

대시보드 UI 담당 범위 안에서 끝나는 항목이라 먼저 정했다.

| 항목 | 결정 | 근거 |
|---|---|---|
| 과업 예시 칩 높이 | **44px**, 라벨을 짧게 써서 한 줄 유지 | 권장 타겟 크기를 지키면서 한 줄을 유지한다. 라벨과 입력 문장을 분리해 "한 문장으로 쓴다"는 유도 효과도 남긴다 |
| 모바일 선택 시 예상 시간 | **이유 문구로 대체** | 숫자가 말없이 사라지면 고장으로 보인다. 보정이 안 된 값을 '보정'이라 쓰지 않는 리포트 원칙과 방향이 같다 |
| 테스트 계정 입력칸 | **비활성으로 두고 M3 이후 지원** | 동결된 `openapi.yaml`의 `TaskCreate`에 "테스트 계정(credentials_ref)은 암호화 저장소가 정해진 뒤 추가 (10장, M3 이후)"라고 적혀 있다. 칸을 지우면 기획서 5장 근거가 사라지고, 그대로 두면 보낼 곳이 없는 값을 받게 된다 |
| 고급 설정 구조 | **접이식 유지, 보류** | 기획서가 반복 횟수를 고급 설정에 두라고 했고, 5회 선택 시 예상 비용·시간을 함께 보여줄 자리가 필요하다. 항목이 추가되면 그때 구조를 다시 본다 |

칩 높이는 공용 칩 컴포넌트를 쓸지 디자인 시스템 담당(리포트 UI)에게 확인한다. 공용 컴포넌트를 쓰면 높이가 그쪽 값에 따라간다.

## 결정이 필요한 사항

다른 역할과 걸려 있어 혼자 정할 수 없다.

1. **예상 시간·비용의 계산 주체 분리** — 시간은 화면 추정, 비용은 서버 응답으로 나누는 제안을 플랫폼 백엔드가 받아들이는지. 비용 조회 실패 시 측정 시작을 막지 않는 것도 함께 확인한다. 분리가 안 되면 요약 열 전체가 로딩 상태를 갖는 구조로 다시 짜야 한다.
