# 0011. W3 계획 보완: 비밀번호 칸, 검출 기준, 예상 소요 시간, 범위, 과업 조회, 재측정

- **날짜:** 2026-11-10 (PM 결정)
- **근거 기록:** 아래 6번 표의 "반영할 곳", 각 폴더 README의 "ADR 0011에 따른 할 일"

## 배경

main `32eb3cb`에서 주간 계획과 코드를 맞춰 보니, 최종 평가(홀드아웃 정밀도·재현율, 사람 기준 소요 시간, 외부 사용자 테스트)에 필요한데 담당과 주차가 없는 항목이 있었다. 이미 들어간 동작이 벤치마크 과업과 어긋나는 곳도 있었다.

- 에이전트는 화면에 비밀번호 칸이 보이면 시도를 `blocked`(login_wall)로 끝낸다(`worker/agent/safety.py`). 개발 앱 정답 24개 중 12개(sb-admin-2 6, material-kit-react 6)와 사람 실험 1·3·4번 페이지가 비밀번호 칸이 있는 화면이라 에이전트가 시작하지 못한다.
- `benchmark/eval.py`는 (케이스, 규칙, 대상) 예측을 채점하지만, 에이전트 run의 이슈 중 무엇을 예측으로 셀지 정해지지 않았다.
- 예상 소요 시간(F09, 개발계획서 5.10)은 주간 계획에 "KLM 보정(선택)"만 있고 문헌값 계산이 없다.
- 측정 생성·진행 화면, 스테이징의 API·워커 배포, 벤치마크를 에이전트로 돌려 채점하는 도구가 계획에 없다.
- 과업 문장과 사이트 주소를 읽는 조회가 API에 없어 리포트 제목이 "과업 #번호"로 나온다. 프로젝트의 과업 목록을 읽는 조회도 없어 측정 목록 화면이 과업을 찾지 못한다.
- 재측정(`auto`)에서 재생이 끊긴 뒤 에이전트를 몇 번 돌리는지 정해지지 않았다(`docs/worker_api_spec.md` 2번). 개발계획서 안에서도 2.2·4.6("반복 횟수 N만큼 독립 실행")과 7.2("그 지점부터 이어받는다")가 다르다.
- 사람 실험 파일을 올리는 `POST /human-sessions`가 구현되지 않았고 계획에도 없다.
- W3에 구현하는 규칙과 지표를 에이전트 루프에서 부르는 연결이 계획에 빠져 있다(W2의 R07과 같은 경우).

## 결정

### 1. 비밀번호 칸

- 화면에 비밀번호 칸이 보인다는 이유만으로 시도를 끝내지 않는다. CAPTCHA·봇 확인 화면은 지금처럼 `blocked`로 끝낸다.
- 비밀번호 칸(`type=password`, 또는 `autocomplete`가 `current-password`·`new-password`)에는 **과업 문장에 그대로 적힌 값만** 입력한다. 에이전트는 값을 지어내지 않는다. 비밀번호 칸을 누르는 것은 막지 않는다.
- 과업 문장에 없는 값을 비밀번호 칸에 넣으려 하면 실행하지 않고 그 시도를 `blocked`, `end_detail=login_wall`로 끝낸다. 계정이 있어야 하는데 값이 없는 과업이라는 뜻이다. 끝내기 전에 형식 오류 때처럼 다시 고르게 할 수 있다(최대 2번).
- 카드 번호·보안 코드 칸(`cc-number`, `cc-csc`)과 되돌릴 수 없는 버튼(결제·삭제·발송)은 지금처럼 `safety_stop`이다.
- 행동 프롬프트에 같은 규칙을 넣고 버전을 올린다: 비밀번호 칸에는 과업에 적힌 값만 넣고, 값이 없는데 로그인·가입이 필요하면 `fail`로 끝낸다.
- 과업 문장에는 가짜 값만 적는다. 실제 계정 정보를 받지 않는다는 [ADR 0004](0004-test-account-after-m3.md)는 그대로다. 측정 생성 화면의 과업 입력칸 옆에 이 안내를 둔다.
- 벤치마크와 사람 실험에서 에이전트에게 주는 과업 문장은 입력값을 포함한 문장으로 고정해 `benchmark/` 아래 한 파일에 둔다. 사람 실험 6페이지는 `human-study/pages.md`의 "참가자에게 주는 과업 문장"과 같은 문장을 쓴다. 사람과 에이전트가 같은 값을 입력해야 입력 글자 수가 같아 예상 소요 시간을 비교할 수 있다.

### 2. 검출로 세는 기준

- **검출:** run의 기본 목록에 뜬 이슈(`is_reference=false`)다. 참고 목록(경로 밖, 점수 임계값 미만)은 검출이 아니다. 리포트가 문제라고 보여 주는 것만 맞힌 것으로 센다.
- **단위:** (케이스, 규칙, 요소) 하나가 1건이다. 3회 시도와 여러 단계에서 같은 것이 여러 번 나와도 1건이다.
- **일치:** 이슈가 가리키는 요소(행동 대상, axe 규칙이면 axe가 짚은 요소)가 정답 selector에 맞는 요소이거나 그 안에 있고, 규칙이 같으면 일치다. 확인 방법은 회귀 비교·인프라 담당이 개발 앱에서 정해 문서로 남기고, 홀드아웃 평가가 끝날 때까지 바꾸지 않는다. 정답 정보는 워커의 판정과 점수 계산에 넘기지 않는다.
- **오탐:** 정상 기준선과 변이 화면 모두에서, 정답과 일치하지 않는 기본 목록 이슈는 오탐이다.
- **채점하는 규칙:** 결함을 주입한 6개(R01·R02·R03·R04·R06·R10)다. 다른 규칙(R05·R07·R08·R09)이 기본 목록에 낸 이슈는 점수에 넣지 않고 건수를 따로 보고한다.
- **두 가지로 채점:** "규칙만"(점수와 관계없이 경로 위 후보 전체)과 "점수 적용"(기본 목록). 성공 기준의 "이슈 점수 적용 후 정밀도 +0.05"는 이 둘의 차이다. 이슈 점수가 생기기 전에는 "규칙만"으로 낸다.
- **보고:** 비율과 함께 맞힘·오탐·놓침 건수를 규칙별로 적는다. 정답이 유형당 몇 개뿐이라 한 건에 비율이 크게 움직인다.
- **베이스라인:** axe 단독과 LLM 스크린샷도 같은 단위와 같은 일치 기준으로 채점한다.
- **고정:** 점수 임계값과 이 기준은 11/27 동결 때 고정하고, 홀드아웃 평가(11/30–12/1)에서 바꾸지 않는다.
- **0차 실행:** W3 안에 개발 앱 4개의 정상 과업 8개와 변이 24개를 `claude-haiku-5-5`로 한 번 돌려 완주율과 "규칙만" 점수를 낸다. 그때까지 돌지 못하는 케이스는 이유와 함께 적는다. W5 개발 앱 1차 평가와 홀드아웃 최종 평가는 `claude-sonnet-5-5`로 한다([ADR 0002](0002-llm-models.md)).

### 3. 예상 소요 시간 (문헌값 KLM)

문헌값 계산은 필수다(F09). 보정 계수와 Fitts 식 대체만 선택 항목이다([ADR 0008](0008-schedule-to-1204.md)). 상수는 개발계획서 5.10 그대로이고(K 0.28, P 1.1, B 0.1, H 0.4, M 1.35, S는 P와 같은 1.1초), 5.10이 정하지 않은 부분만 여기서 정한다.

| 행동 | 시간 |
|---|---|
| click, back | M + P + 2B = 2.65초 |
| type | M + P + 2B + H + K × 입력 글자 수 |
| select | M + 2P + 4B = 3.95초 (열기와 고르기) |
| scroll | M + S = 2.45초 |
| wait, done, fail | 0 |

- 그 화면에서 처음 하는 행동이면 M을 1회 더한다. 시도의 첫 행동도 해당한다. 화면 구분은 [ADR 0009](0009-r06-first-target.md)와 같다(출처+경로).
- 직전 행동이 type이고 이번 행동이 click·type·select·scroll·back이면 H를 1회 더한다(키보드에서 마우스로).
- 대상이 화면 밖이라 드라이버가 스크롤해야 했으면 S를 1회 더한다.
- **R(시스템 응답)은 넣지 않는다.** 응답 시간은 네트워크에 따라 흔들려 같은 경로를 다시 재생해도 값이 달라지고, 재생 비교의 "2회 값 일치"(7.2)가 깨진다. 리포트에는 "문헌값 기준 추정 · 시스템 응답 시간 제외"로 표시한다.
- 예: 새 화면에서 16자를 입력하고 버튼을 누르면 type 2M + P + 2B + H + 16K = 8.88초, click H + M + P + 2B = 3.05초, 합 11.93초다.
- 단계 값은 `Step.est_seconds`, 시도 합계는 지표 `est_task_time`(초)에 저장한다. run 값은 다른 지표처럼 성공한 시도의 중앙값이다. 모바일은 계산하지 않는다.
- **사람 측정값과 비교(필수):** 사람 실험 6페이지에서 참가자 과업 시간의 중앙값과 같은 페이지 run의 `est_task_time`을 비교해 평균 오차율과 스피어만 순위 상관을 낸다(9.1 검증의 A 조건). 예측에 R이 없으므로 사람 쪽도 R 구간을 뺀다. 과업 시간을 어디서 어디까지로 볼지는 결과를 보기 전에 `ml/timing/README.md`에 적는다.
- **사람 쪽 화면 안정 시점:** 수집 기록의 `stable`은 마우스를 올리기만 해도 생길 수 있다(`human-study/README.md` "알려진 한계"). 수집 스크립트는 바꾸지 않는다. 분석에서 click·key 뒤에 처음 나온 `stable`만 화면 안정 시점으로 쓰고, 다음 행동 전까지 더 나온 `stable`은 쓰지 않는다.

### 4. 범위

이번 일정에서 만들지 않는 것:

- **재생 확인 화면과 대응 관계 저장**(`/tasks/{id}/aliases`): 성공 기준이 "사용자 확인 없이 10개 중 8개 재생"이라 수치에 들어가지 않는다. 재생이 끊기면 끊긴 지점을 보여 주는 데까지만 한다.
- **라벨 입력 화면**(`/issues/{id}/label`): 실사이트 약 20건은 스프레드시트로 2명이 판정하고, 결과 CSV와 일치도(κ) 계산은 `ml/` 아래에 둔다.
- **다른 출처 iframe과 닫힌 shadow root 수집 보완:** 한계로 둔다. 실제 SPA 3개 스트레스 테스트 합격(3.1)은 정답의 사람 검토가 끝나지 않아 미완료다. 수집 품질은 개발 앱 0차 실행 결과로 먼저 보고, 수집 누락 때문에 실패한 케이스가 나오면 그때 다룬다.
- **사람 실험 세션 업로드**(`/human-sessions`): 사람 측정값과 예측값 비교는 수집한 JSON 파일로 바로 한다. 파일은 저장소에 올리지 않고, 팀 Notion에서 팀원만 볼 수 있는 페이지로 넘긴다. 보관 기한(2026-12-31)이 지나거나 참가자가 철회하면 그 페이지의 파일도 지운다(동의서 5·6절).

줄이는 것:

- **측정 이력(F11):** 측정 목록이 필수이고 추이 차트는 선택이다.
- **외부 사용자 테스트 1차(11/18–11/21):** 운영자가 측정을 만들어 주고 참가 팀은 리포트를 본다. 측정 생성·진행 화면은 M3(11/22)까지 만들어 2차(11/23–11/26)부터 팀이 직접 쓴다.

만들지 않는 경로는 `apps/api/openapi.yaml`에 남겨 둔다. 스키마에서 바꾸는 것은 7번의 조회 두 개와 8번의 설명 문구뿐이다.

### 5. 화면 변화 없이 서버 응답만 있는 행동

- 행동 뒤 화면 변화는 없고 유효한 서버 응답만 확인되면 `effect_type=dom_mutation`, `changed=true`로 저장한다. 무반응(R03)으로 보지 않는다(개발계획서 5.1 "POST·PUT·PATCH·DELETE는 항상 유효한 반응").
- 지금은 이 경우 `UnclassifiedNetworkEffect`로 시도가 error로 끝난다. 동결된 `effect_type` 네 값은 바꾸지 않는다.

### 7. 과업 조회

- `GET /tasks/{id}`(과업 하나)와 `GET /projects/{id}/tasks`(프로젝트의 과업 목록)를 `apps/api/openapi.yaml`에 더한다. 응답은 이미 있는 `Task` 형식을 그대로 쓴다. 기존 경로와 응답은 바꾸지 않는다.
- 요청한 초대 코드의 프로젝트에 속한 과업만 돌려준다. 아니면 다른 경로처럼 404다.
- 리포트는 `run.task_id`로 과업 문장을 읽고, 과업의 `project_id`를 `GET /projects` 결과에서 찾아 사이트 주소를 읽는다. 측정 목록 화면은 과업 목록에서 과업을 고른 뒤 `GET /tasks/{id}/runs`를 부른다.
- `openapi.yaml` 변경은 CODEOWNERS 승인을 받는 PR로 한다. 목 JSON과 화면 타입(`npm run gen:api`)을 같이 맞춘다.

### 8. 재측정(`auto`)에서 재생이 끊기면

- 기준 run의 대표 경로를 먼저 재생한다(`kind=replay`). 끝까지 재생되면 에이전트는 돌리지 않는다.
- 재생이 끊기면 그 시도는 끊긴 지점과 함께 남기고(`replay_status=partial`), 에이전트로 처음부터 `repeat_n`회 다시 잰다(`kind=agent`). 끊긴 지점에서 이어 가지 않는다.
- run 단위 지표는 성공한 에이전트 시도의 중앙값이다. 재생 값과 섞지 않는다(`save_run_medians`의 kind 구분 그대로).
- 에이전트 시도의 병렬 실행은 재생이 끝난 뒤에 시작한다.
- 진행률의 예정 시도 수는 재생이 끊기면 재생 시도 수에 `repeat_n`을 더한 값이다.
- 개발계획서 2.2·4.6과 같고, 7.2의 "그 지점부터 에이전트가 이어받는다"와 `openapi.yaml` RunMode 설명("끊기면 그 지점부터 에이전트")과 다르다. 값과 형식은 그대로이고 설명 문구만 다르므로 7번 PR에서 같이 고친다.

### 9. Sonnet 평가 비용 (2026-11-18 추가)

- W5 개발 앱 1차 평가와 홀드아웃 최종 평가는 2번 결정대로 `claude-sonnet-5-5`로 한다.
- 비용은 API 프로모션 크레딧 $100으로 충당한다. 크레딧은 2026-12-17에 만료된다.
- 예상 비용은 0차 실행([benchmark/w3.md](../../benchmark/w3.md) "0차 실행 결과")의 실제 토큰 사용량에 `worker/llm/pricing.py`의 Sonnet 단가를 곱한 값이다.
  - 0차 실행은 개발 앱 32케이스 × 3회, LLM 호출 737회, 입력 3,562,060토큰(캐시 포함), 출력 266,231토큰, Haiku 비용 $0.3710이다. 100K 토큰을 넘은 요청은 없었다.
  - `llm_call`에는 입력 합계만 남고 캐시 쓰기·읽기 구분이 없다. `pricing.py`의 Sonnet 단가는 항목마다 Haiku 짧은 프롬프트 단가의 정확히 20배다(입력 2.00/0.10, 출력 10.00/0.50, 캐시 쓰기 2.50/0.125, 캐시 읽기 0.20/0.01). 그래서 같은 토큰의 Sonnet 비용은 호출마다 Haiku 비용 × 20이다(100K 초과 요청이면 × 4).
  - 1회 평가(개발 앱 32케이스 × 3회): $0.3710 × 20 = **$7.42**. 캐시를 전혀 쓰지 못한다고 보면 (3,562,060 × $2.00 + 266,231 × $10.00) / 1,000,000 = $9.79다.
  - 계획된 횟수는 W5 개발 앱 1차 평가 1회와 홀드아웃 최종 평가 1회다([ADR 0008](0008-schedule-to-1204.md)). 홀드아웃 케이스 수는 공개 저장소에 적지 않으므로 개발 앱 1회분과 같다고 가정한다. 합계 $7.42 × 2 = **$14.84**(캐시 없음 기준 $19.57)다.
  - Sonnet은 도구 선택을 강제하지 않으므로(`worker/llm/claude.py`) 출력 토큰이 늘 수 있다. 출력이 3배가 돼도 1회 $12.75, 합계 $25.49다. 크레딧 $100은 1회 $7.42 기준 13회분이다.
- 모든 Sonnet 평가(W5 11/23–11/29, 홀드아웃 11/30–12/1)는 크레딧 만료 전에 끝난다.
- **실측(2026-11-18, `dcf1766`):** Sonnet으로 개발 앱 32케이스 × 3회를 한 번 평가한 비용은 **$10.17**(run당 $0.318)이다([benchmark/w3.md](../../benchmark/w3.md) "0차 재실행"). 예상 $7.42의 1.37배다.
  - 호출 907회, 입력 4,541,569토큰, 출력 401,300토큰이다. Haiku가 형식 오류로 일찍 끝나던 shadcn-admin에서 Sonnet은 loop·gave_up까지 진행해 호출과 출력이 늘었다.
  - 실측으로 다시 잡은 계획 2회 합계는 $10.17 × 2 = **$20.33**이다(홀드아웃 가정은 위와 같다).
  - 크레딧 사용액은 평가 DB `llm_call` 기록 기준 **$12.65**, 남은 금액은 **$87.35**다. Sonnet $11.88은 채점한 32 run $10.17, 사전 시험 $1.14, 다시 돌린 run $0.57이다. Haiku $0.77은 0차와 사전 시험 $0.40, 재실행 $0.37이다. Console 잔액과 다르면 Console 값을 따른다.
  - Console의 API 사용 한도에 걸려(기록 기준 누적 $4.94) 호출이 400("specified API usage limits", 12/1 재개 안내)으로 거절된 적이 있다. 같은 날 한도를 올려 재개했다. W5·홀드아웃 평가 전에 월 사용 한도가 남은 계획 비용보다 큰지 확인한다.

## 대안

- 비밀번호 칸을 localhost에서만 허용한다: 스테이징에 올린 벤치마크와, 사용자가 가짜 값으로 자기 로그인 폼을 재는 경우를 막는다.
- 비밀번호 칸을 조건 없이 허용한다: 에이전트가 값을 지어내 실제 사이트에 가입·로그인을 시도할 수 있다.
- 심각도 높음만 검출로 센다: 중간 등급인 R06·R10 정답을 놓친 것으로 세게 된다.
- 참고 목록까지 검출로 센다: 리포트에서 문제로 보여 주지 않는 것을 맞혔다고 세게 된다.
- R을 예상 소요 시간에 넣는다: 같은 버전을 다시 재도 값이 달라져 전후 비교에 쓸 수 없다.
- 서버 응답만 있는 경우를 위해 `effect_type`에 값을 더한다: 동결 스키마·DB·화면 타입을 모두 바꿔야 한다.
- 과업 조회를 더하지 않는다: 리포트 제목이 "과업 #번호"로 남고, 측정 목록 화면이 최근에 잰 과업만 찾을 수 있다.
- `POST /human-sessions`를 만든다: 비교 계산에 필요하지 않고, 참가자 자료가 스테이징 서버에 한 벌 더 생긴다.
- 수집 스크립트에서 속성 변경을 빼 `stable`을 줄인다: 본 수집 직전에 수집 코드를 바꾸면 6페이지 확인을 다시 해야 하고(`human-study/session-procedure.md`), 파일럿 자료와 기준이 달라진다. 속성만 바뀌어 열리는 메뉴의 화면 변화도 놓친다.
- 재생이 끊긴 지점부터 에이전트 1회로 이어 간다: 시도가 1회라 중앙값과 편차가 없어 전후 비교 판정에 쓸 수 없다. 재생 구간과 에이전트 구간이 섞인 기록의 지표 계산도 새로 정해야 한다.

### 10. #75 관찰 누락: 수집 역할, 30개 정렬, 입력 후 Enter (PM 결정, 2026-11-23 반영)

근거: [#75](https://github.com/hanchaehun/StepMeter/issues/75). 0차 재실행에서 shadcn-admin 정상 과업 2개가
Haiku·Sonnet 모두 0/3이었다. 원인은 모델이 아니라 에이전트가 받는 요소 목록이었다
(cmdk·Radix의 `role=option` 미수집, 모달 뒤 가려진 main 요소가 30칸 차지, Enter 행동 없음).
PM이 이슈에서 수집 역할 추가와 `worker/schemas.py`·`docs/action_schema_spec.md` 변경을 승인했다.

- **수집 역할:** `worker/collect/src/collect.js`의 수집 대상에 `option`, `menuitemcheckbox`, `menuitemradio`, `radio`,
  `switch`, `combobox`, `treeitem`, `slider`, `spinbutton`, `searchbox`, `textbox` 역할 속성을 더한다. tabindex가 없거나
  -1이어도 보이면 수집한다. `benchmark/baseline_llm.py`(LLM 베이스라인)와 `human-study/collect.js`(사람 실험 수집)의
  목록은 비교 기준이라 바꾸지 않는다. `docs/element_snapshot_spec.md`에는 역할 목록이 없어 고칠 문구가 없다.
- **30개 정렬:** 요소가 30개 이하면 문서 순서 그대로 보낸다. 넘으면 ① 열린 겹침 층 안의 요소(가장 가까운 조상이
  `dialog[open]`, `[role=dialog]`, `[role=alertdialog]`, `[aria-modal="true"]`, `[role=listbox]`, `[role=menu]`)
  ② 가려지지 않은 요소 ③ 텍스트 입력칸(input text·email·search·password·tel·url·number, textarea, 역할 textbox·searchbox·
  combobox) ④ 기존 기준(main 안, 화면 중심 거리, 큰 순, el_id) 순이다. 겹침 층·텍스트 입력 여부는 `observe()` 행의 정렬
  전용 필드 `sort`로 넘기고 LLM에 보내는 항목에서는 뺀다. 30개 안의 가려진 요소는 1번 결정대로 `"(가려짐)"`이다.
- **입력 후 Enter:** `TypeAction`에 `submit: bool = False`를 더한다. `submit=true`면 입력 후 같은 요소에서 Enter를
  한 번 누르며, 입력과 Enter는 한 번의 효과 관찰 안에서 일어난다. 비밀번호 칸 규칙(1번)은 지금처럼 먼저 돈다.
  `submit`이 없는 예전 기록은 `False`로 재생한다.
  Enter 제출도 click과 같은 되돌릴 수 없는 버튼 검사를 거친다(2026-11-23 추가): 후보는 폼이 있으면 기본 제출 버튼(`form.elements`의 첫 제출 버튼, `form=` 속성 포함, 없으면 폼의 aria-label·name·title), 폼이 없으면(textarea·contenteditable 포함) 조상 3단계 안의 button·[role=button]·input[type=submit]이고, 하나라도 걸리면 Enter 전에 `safety_stop`이다. 후보가 없으면 그대로 진행한다.
  재생 측정도 KLM 예상 시간(단계 `est_seconds`, 시도 `est_task_time`)을 3번 규칙대로 저장해 재생 비교에서 `est_task_time`을 판정한다(2026-11-23 추가, 모바일 제외).
  `openapi.yaml`은 "worker/schemas.py에서 생성" 블록만 다시 만들고
  (`python -m tests.test_openapi_schema`), 화면 타입은 `npm run gen:api`로 다시 만든다. 경로·응답·다른 스키마는 그대로다.
- **도구와 응답 정리:** `choose_action`은 strict라 `submit`을 properties와 required에 넣고 `boolean | null`로 받는다.
  `extract_text`는 null 항목을 빼던 규칙에 더해, `type`이 아닌 행동의 `submit`이 false면 뺀다. `type`이 아닌데
  true면 그대로 두어 형식 검사가 거절하게 한다(모델 실수). 다시 물을 때 고른 행동에 없는 필드 이름을 알려 준다.
- **프롬프트:** `prompts/action_v3.md` = `action_v2` + `submit` 설명 한 단락. Run·LlmCall의 `prompt_version`은
  `action_v3`다. `action_v2.md`는 기록 재현을 위해 남긴다.
- **KLM:** 3번 표의 type에 `submit=true`면 K를 1회 더한다(#78에서 구현, 이번에 확인만 했다).
- 재측정 결과는 [benchmark/w3.md](../../benchmark/w3.md) "#75 수정 후 재측정 (2026-11-23)"에 있다.


### 11. 관찰·반응 판정 보강 (PM 결정, 2026-11-25)

근거: main `d1aed02` 위의 W5 품질 점검. 재측정 결과는 [benchmark/w3.md](../../benchmark/w3.md) "관찰·반응 판정 보강 후 재측정 (2026-11-25)"에 있다.

- **요소 상한 60, 한 줄 형식, 상태 표시 (`action_v4`):** LLM에 보내는 요소는 최대 60개다(1번·10번의 30을 바꾼다. 고르는 순서는 10번 그대로). 요소마다 `번호|역할(없으면 태그)|이름(없으면 label_text)|영역(없으면 -)|x,y,너비x높이(정수)|표시` 한 줄로 보낸다. 표시는 가려짐·입력됨·비어 있음·선택됨·펼쳐짐·비활성이고, select는 줄 끝에 옵션 목록을 붙인다. 상태는 `observe()` 행의 `state`(true/false)로 받고, 입력값은 어디에도 넣지 않는다. cmdk 항목(`[cmdk-item]`)의 `aria-selected`는 체크 상태가 아니라 커서 위치라 선택됨으로 보이지 않는다. 이름·옵션 글자 안의 `|`는 `/`로 바꾼다. `state`는 `state_hash`·매칭 지문·ElementSnapshot에 넣지 않는다. 최근 행동에는 대상의 `target_name`(`역할:이름`)을 남긴다. Run·LlmCall의 `prompt_version`은 `action_v4`다.
- **첫 화면 안정화 대기:** 에이전트와 재생 모두 `goto` 직후 `record_first_view` 전에 `wait_for_dom_quiet(page, quiet_ms=200, min_ms=400, max_ms=1500)`를 부른다. 시작 후 400ms가 지났고, 마지막 DOM 변화(추가·삭제·속성 변경) 뒤 200ms 동안 조용하고, `document.readyState`가 complete면 끝낸다. 1500ms가 되면 조건과 상관없이 끝낸다. 다른 대기(이동 뒤 0.5초 등)는 바꾸지 않는다. 한계: 400ms 넘게 아무 변화가 없다가 그 뒤에 그려지는 내용은 첫 관찰에 안 잡힐 수 있다.
- **행동 준비를 관찰 창 밖으로:** 대상 재확인·옵션 확인·안전 검사는 효과 관찰 스크립트를 설치한 뒤, 3초 관찰 창을 시작하기 전에 한다. 실제 입력(click·fill·press·select_option·뒤로 가기)에는 Playwright 시간 제한 2500ms(관찰 창의 5/6)를 주어 브라우저 쪽에서 취소되게 하고, 관찰 창의 `asyncio.wait_for`는 안전망으로 남긴다. 입력 후 Enter는 fill과 하나의 마감을 나눠 써서, Enter에는 2500ms에서 fill이 쓴 시간을 뺀 나머지(최소 100ms)만 준다. 에이전트는 `perform`에서 Playwright `TimeoutError`가 나면 stale `el_id`처럼 다시 관찰해 모델이 다시 고르게 한다(같은 3회 한도, 넘으면 `error`, `TimeoutError@perform`). 재생은 지금처럼 `partial`이다.
- **숨긴 select 제외:** 요소 자신이 `aria-hidden="true"`이고 1px 이하로 잘린 요소(Radix Select의 숨긴 native select)는 수집하지 않는다. 조상의 `aria-hidden`(모달 배경)과 aria-hidden이 없는 sr-only 입력칸은 그대로 수집한다.
- **보정 자료의 참고 후보:** `score_development --calibration-output`은 규칙이 참고로 낸 후보(데스크톱 R01 44px 권장, 9번)를 `was_reference=true`로 남긴다. `ml/issue_clf/calibrate.py`의 비교 기준(`rules_only`)에서도 이 행을 뺀다. 그래서 이슈 점수의 정밀도 차이는 기본 목록끼리의 비교다.
- 이 결정 전에 기록된 기준 경로는 첫 화면·화면 해시·반응 판정이 달라 재생이 끊길 수 있다. 버전 비교 전에 기준을 다시 잰다.

### 12. 이슈 점수 미적용으로 동결 (PM 결정, 2026-11-26)

근거: W5 Sonnet 개발 앱 1차 평가(main `e88c961`, `claude-sonnet-5-5`, 32케이스 × 3회, [benchmark/w3.md](../../benchmark/w3.md) "W5 Sonnet 개발 앱 1차 평가 (2026-11-25)")와 그 보정 자료(`calibration.json`)로 한 이슈 점수 분석(#91).

- **동결:** 11/27에 이슈 점수 설정(`STEPMETER_ISSUE_SCORE_CONFIG`) 없이 동결한다. 기본 목록은 규칙이 정한 기본/참고 구분 그대로다. 홀드아웃 최종 평가(11/30–12/1)도 같은 조건으로 돌린다.
- **이유:** 기본 목록 23/10/1(정탐/오탐/미탐)에서 오탐 10건은 모두 점수 항목이 어떤 정탐 이상이라, 가중치와 임계값을 어떻게 정해도 정탐을 잃지 않고는 뺄 수 없었다. 0.1 간격 탐색에서 22/8/2, 21/6/3은 가능했지만 R06·R03 정탐을 잃었고, 앱 하나를 빼고 고르는 검증에서도 꾸준한 개선이 없었다.
- **보고 방식:** 2번의 성공 기준 "이슈 점수 적용 후 정밀도 +0.05"는 이슈 점수 효과를 보려던 기준이다. 점수를 쓰지 않으므로 "이슈 점수 미적용, +0.05 미달성"으로 보고한다.
  "규칙만" 정밀도 0.250(23/69/1)과 "기본 목록" 0.697(23/10/1)의 차이(+44.7%p)는 점수 효과가 아니다. 데스크톱 R01 44px 권장 후보를 참고로 분리한 규칙 결정(9번 "데스크톱 R01 44px 권장 후보를 참고로 분리") 효과이므로 그렇게 따로 적는다.
- **정답 밖 실제 문제:** 기본 목록 R03 오탐 9건 중 7건은 react-shopping-cart의 검색 버튼이다. 누르면 화면에 변화가 없는 실제 동작이라 R03 판정 자체는 맞다([docs/w4-metrics-review.md](../w4-metrics-review.md)). 정답 파일이 주입한 결함만 담아 오탐으로 센다. 검색은 입력 중에 이미 실행되므로 UX 문제로 볼지는 판단이 갈린다. 정답 파일은 홀드아웃 평가가 끝날 때까지 바꾸지 않는다.
- 개발 앱은 개발 중에 여러 번 본 자료라 이 수치는 낙관적이다. 최종 정밀도·재현율은 홀드아웃 결과로 낸다.
