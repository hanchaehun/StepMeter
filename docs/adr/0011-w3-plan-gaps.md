# 0011. W3 계획 보완: 비밀번호 칸, 검출 기준, 예상 소요 시간, 범위, 과업 조회, 재측정

- **날짜:** 2026-11-10 (PM 결정)
- **근거 기록:** 아래 6번 표의 "반영할 곳", 각 폴더 README의 "ADR 0011에 따른 할 일"

## 배경

main `32eb3cb`에서 주간 계획과 코드를 맞춰 보니, 최종 평가(홀드아웃 정밀도·재현율, 사람 기준 소요 시간, 외부 사용자 테스트)에 필요한데 담당과 주차가 없는 항목이 있었다. 이미 들어간 동작이 벤치마크 과업과 어긋나는 곳도 있었다.

- 에이전트는 화면에 비밀번호 칸이 보이면 시도를 `blocked`(login_wall)로 끝낸다(`worker/agent/safety.py`). 개발 앱 정답 24개 중 12개(sb-admin-2 6, material-kit-react 6)와 사람 실험 1·3·4번 페이지가 비밀번호 칸이 있는 화면이라 에이전트가 시작하지 못한다.
- `benchmark/eval.py`는 (케이스, 규칙, 대상) 예측을 채점하지만, 에이전트 run의 이슈 중 무엇을 예측으로 셀지 정해지지 않았다.
- 예상 소요 시간(F09, 개발계획서 5.10)은 주간 계획에 "KLM 보정(선택)"만 있고 문헌값 계산이 없다.
- 측정 생성·진행 화면, 스테이징의 API·워커 배포, 벤치마크를 에이전트로 돌려 채점하는 도구가 계획에 없다.
- 과업 문장과 사이트 주소를 읽는 조회가 API에 없어 리포트 제목이 "과업 #번호"로 나온다. 프로젝트의 과업 목록을 읽는 조회도 없어 측정 목록 화면이 과업을 찾지 못한다.
- 재측정(`auto`)에서 재생이 끊긴 뒤 에이전트를 몇 번 돌리는지 정해지지 않았다(`docs/worker_api_spec.md` 2번). 개발계획서 안에서도 2.2·4.6("반복 횟수 N만큼 독립 실행")과 7.2("그 지점부터 이어받는다")가 다르다.
- 사람 실험 파일을 올리는 `POST /human-sessions`가 구현되지 않았고 계획에도 없다.
- W3에 구현하는 규칙과 지표를 에이전트 루프에서 부르는 연결이 계획에 빠져 있다(W2의 R07과 같은 경우).

## 결정

### 1. 비밀번호 칸

- 화면에 비밀번호 칸이 보인다는 이유만으로 시도를 끝내지 않는다. CAPTCHA·봇 확인 화면은 지금처럼 `blocked`로 끝낸다.
- 비밀번호 칸(`type=password`, 또는 `autocomplete`가 `current-password`·`new-password`)에는 **과업 문장에 그대로 적힌 값만** 입력한다. 에이전트는 값을 지어내지 않는다. 비밀번호 칸을 누르는 것은 막지 않는다.
- 과업 문장에 없는 값을 비밀번호 칸에 넣으려 하면 실행하지 않고 그 시도를 `blocked`, `end_detail=login_wall`로 끝낸다. 계정이 있어야 하는데 값이 없는 과업이라는 뜻이다. 끝내기 전에 형식 오류 때처럼 다시 고르게 할 수 있다(최대 2번).
- 카드 번호·보안 코드 칸(`cc-number`, `cc-csc`)과 되돌릴 수 없는 버튼(결제·삭제·발송)은 지금처럼 `safety_stop`이다.
- 행동 프롬프트에 같은 규칙을 넣고 버전을 올린다: 비밀번호 칸에는 과업에 적힌 값만 넣고, 값이 없는데 로그인·가입이 필요하면 `fail`로 끝낸다.
- 과업 문장에는 가짜 값만 적는다. 실제 계정 정보를 받지 않는다는 [ADR 0004](0004-test-account-after-m3.md)는 그대로다. 측정 생성 화면의 과업 입력칸 옆에 이 안내를 둔다.
- 벤치마크와 사람 실험에서 에이전트에게 주는 과업 문장은 입력값을 포함한 문장으로 고정해 `benchmark/` 아래 한 파일에 둔다. 사람 실험 6페이지는 `human-study/pages.md`의 "참가자에게 주는 과업 문장"과 같은 문장을 쓴다. 사람과 에이전트가 같은 값을 입력해야 입력 글자 수가 같아 예상 소요 시간을 비교할 수 있다.

### 2. 검출로 세는 기준

- **검출:** run의 기본 목록에 뜬 이슈(`is_reference=false`)다. 참고 목록(경로 밖, 점수 임계값 미만)은 검출이 아니다. 리포트가 문제라고 보여 주는 것만 맞힌 것으로 센다.
- **단위:** (케이스, 규칙, 요소) 하나가 1건이다. 3회 시도와 여러 단계에서 같은 것이 여러 번 나와도 1건이다.
- **일치:** 이슈가 가리키는 요소(행동 대상, axe 규칙이면 axe가 짚은 요소)가 정답 selector에 맞는 요소이거나 그 안에 있고, 규칙이 같으면 일치다. 확인 방법은 회귀 비교·인프라 담당이 개발 앱에서 정해 문서로 남기고, 홀드아웃 평가가 끝날 때까지 바꾸지 않는다. 정답 정보는 워커의 판정과 점수 계산에 넘기지 않는다.
- **오탐:** 정상 기준선과 변이 화면 모두에서, 정답과 일치하지 않는 기본 목록 이슈는 오탐이다.
- **채점하는 규칙:** 결함을 주입한 6개(R01·R02·R03·R04·R06·R10)다. 다른 규칙(R05·R07·R08·R09)이 기본 목록에 낸 이슈는 점수에 넣지 않고 건수를 따로 보고한다.
- **두 가지로 채점:** "규칙만"(점수와 관계없이 경로 위 후보 전체)과 "점수 적용"(기본 목록). 성공 기준의 "이슈 점수 적용 후 정밀도 +0.05"는 이 둘의 차이다. 이슈 점수가 생기기 전에는 "규칙만"으로 낸다.
- **보고:** 비율과 함께 맞힘·오탐·놓침 건수를 규칙별로 적는다. 정답이 유형당 몇 개뿐이라 한 건에 비율이 크게 움직인다.
- **베이스라인:** axe 단독과 LLM 스크린샷도 같은 단위와 같은 일치 기준으로 채점한다.
- **고정:** 점수 임계값과 이 기준은 11/27 동결 때 고정하고, 홀드아웃 평가(11/30–12/1)에서 바꾸지 않는다.
- **0차 실행:** W3 안에 개발 앱 4개의 정상 과업 8개와 변이 24개를 `claude-haiku-5-5`로 한 번 돌려 완주율과 "규칙만" 점수를 낸다. 그때까지 돌지 못하는 케이스는 이유와 함께 적는다. W5 개발 앱 1차 평가와 홀드아웃 최종 평가는 `claude-sonnet-5-5`로 한다([ADR 0002](0002-llm-models.md)).

### 3. 예상 소요 시간 (문헌값 KLM)

문헌값 계산은 필수다(F09). 보정 계수와 Fitts 식 대체만 선택 항목이다([ADR 0008](0008-schedule-to-1204.md)). 상수는 개발계획서 5.10 그대로이고(K 0.28, P 1.1, B 0.1, H 0.4, M 1.35, S는 P와 같은 1.1초), 5.10이 정하지 않은 부분만 여기서 정한다.

| 행동 | 시간 |
|---|---|
| click, back | M + P + 2B = 2.65초 |
| type | M + P + 2B + H + K × 입력 글자 수 |
| select | M + 2P + 4B = 3.95초 (열기와 고르기) |
| scroll | M + S = 2.45초 |
| wait, done, fail | 0 |

- 그 화면에서 처음 하는 행동이면 M을 1회 더한다. 시도의 첫 행동도 해당한다. 화면 구분은 [ADR 0009](0009-r06-first-target.md)와 같다(출처+경로).
- 직전 행동이 type이고 이번 행동이 click·type·select·scroll·back이면 H를 1회 더한다(키보드에서 마우스로).
- 대상이 화면 밖이라 드라이버가 스크롤해야 했으면 S를 1회 더한다.
- **R(시스템 응답)은 넣지 않는다.** 응답 시간은 네트워크에 따라 흔들려 같은 경로를 다시 재생해도 값이 달라지고, 재생 비교의 "2회 값 일치"(7.2)가 깨진다. 리포트에는 "문헌값 기준 추정 · 시스템 응답 시간 제외"로 표시한다.
- 예: 새 화면에서 16자를 입력하고 버튼을 누르면 type 2M + P + 2B + H + 16K = 8.88초, click H + M + P + 2B = 3.05초, 합 11.93초다.
- 단계 값은 `Step.est_seconds`, 시도 합계는 지표 `est_task_time`(초)에 저장한다. run 값은 다른 지표처럼 성공한 시도의 중앙값이다. 모바일은 계산하지 않는다.
- **사람 측정값과 비교(필수):** 사람 실험 6페이지에서 참가자 과업 시간의 중앙값과 같은 페이지 run의 `est_task_time`을 비교해 평균 오차율과 스피어만 순위 상관을 낸다(9.1 검증의 A 조건). 예측에 R이 없으므로 사람 쪽도 R 구간을 뺀다. 과업 시간을 어디서 어디까지로 볼지는 결과를 보기 전에 `ml/timing/README.md`에 적는다.
- **사람 쪽 화면 안정 시점:** 수집 기록의 `stable`은 마우스를 올리기만 해도 생길 수 있다(`human-study/README.md` "알려진 한계"). 수집 스크립트는 바꾸지 않는다. 분석에서 click·key 뒤에 처음 나온 `stable`만 화면 안정 시점으로 쓰고, 다음 행동 전까지 더 나온 `stable`은 쓰지 않는다.

### 4. 범위

이번 일정에서 만들지 않는 것:

- **재생 확인 화면과 대응 관계 저장**(`/tasks/{id}/aliases`): 성공 기준이 "사용자 확인 없이 10개 중 8개 재생"이라 수치에 들어가지 않는다. 재생이 끊기면 끊긴 지점을 보여 주는 데까지만 한다.
- **라벨 입력 화면**(`/issues/{id}/label`): 실사이트 약 20건은 스프레드시트로 2명이 판정하고, 결과 CSV와 일치도(κ) 계산은 `ml/` 아래에 둔다.
- **다른 출처 iframe과 닫힌 shadow root 수집 보완:** 한계로 둔다. 실제 SPA 3개 스트레스 테스트 합격(3.1)은 정답의 사람 검토가 끝나지 않아 미완료다. 수집 품질은 개발 앱 0차 실행 결과로 먼저 보고, 수집 누락 때문에 실패한 케이스가 나오면 그때 다룬다.
- **사람 실험 세션 업로드**(`/human-sessions`): 사람 측정값과 예측값 비교는 수집한 JSON 파일로 바로 한다. 파일은 저장소에 올리지 않고, 팀 Notion에서 팀원만 볼 수 있는 페이지로 넘긴다. 보관 기한(2026-12-31)이 지나거나 참가자가 철회하면 그 페이지의 파일도 지운다(동의서 5·6절).

줄이는 것:

- **측정 이력(F11):** 측정 목록이 필수이고 추이 차트는 선택이다.
- **외부 사용자 테스트 1차(11/18–11/21):** 운영자가 측정을 만들어 주고 참가 팀은 리포트를 본다. 측정 생성·진행 화면은 M3(11/22)까지 만들어 2차(11/23–11/26)부터 팀이 직접 쓴다.

만들지 않는 경로는 `apps/api/openapi.yaml`에 남겨 둔다. 스키마에서 바꾸는 것은 7번의 조회 두 개와 8번의 설명 문구뿐이다.

### 5. 화면 변화 없이 서버 응답만 있는 행동

- 행동 뒤 화면 변화는 없고 유효한 서버 응답만 확인되면 `effect_type=dom_mutation`, `changed=true`로 저장한다. 무반응(R03)으로 보지 않는다(개발계획서 5.1 "POST·PUT·PATCH·DELETE는 항상 유효한 반응").
- 지금은 이 경우 `UnclassifiedNetworkEffect`로 시도가 error로 끝난다. 동결된 `effect_type` 네 값은 바꾸지 않는다.

### 7. 과업 조회

- `GET /tasks/{id}`(과업 하나)와 `GET /projects/{id}/tasks`(프로젝트의 과업 목록)를 `apps/api/openapi.yaml`에 더한다. 응답은 이미 있는 `Task` 형식을 그대로 쓴다. 기존 경로와 응답은 바꾸지 않는다.
- 요청한 초대 코드의 프로젝트에 속한 과업만 돌려준다. 아니면 다른 경로처럼 404다.
- 리포트는 `run.task_id`로 과업 문장을 읽고, 과업의 `project_id`를 `GET /projects` 결과에서 찾아 사이트 주소를 읽는다. 측정 목록 화면은 과업 목록에서 과업을 고른 뒤 `GET /tasks/{id}/runs`를 부른다.
- `openapi.yaml` 변경은 CODEOWNERS 승인을 받는 PR로 한다. 목 JSON과 화면 타입(`npm run gen:api`)을 같이 맞춘다.

### 8. 재측정(`auto`)에서 재생이 끊기면

- 기준 run의 대표 경로를 먼저 재생한다(`kind=replay`). 끝까지 재생되면 에이전트는 돌리지 않는다.
- 재생이 끊기면 그 시도는 끊긴 지점과 함께 남기고(`replay_status=partial`), 에이전트로 처음부터 `repeat_n`회 다시 잰다(`kind=agent`). 끊긴 지점에서 이어 가지 않는다.
- run 단위 지표는 성공한 에이전트 시도의 중앙값이다. 재생 값과 섞지 않는다(`save_run_medians`의 kind 구분 그대로).
- 에이전트 시도의 병렬 실행은 재생이 끝난 뒤에 시작한다.
- 진행률의 예정 시도 수는 재생이 끊기면 재생 시도 수에 `repeat_n`을 더한 값이다.
- 개발계획서 2.2·4.6과 같고, 7.2의 "그 지점부터 에이전트가 이어받는다"와 `openapi.yaml` RunMode 설명("끊기면 그 지점부터 에이전트")과 다르다. 값과 형식은 그대로이고 설명 문구만 다르므로 7번 PR에서 같이 고친다.

## 대안

- 비밀번호 칸을 localhost에서만 허용한다: 스테이징에 올린 벤치마크와, 사용자가 가짜 값으로 자기 로그인 폼을 재는 경우를 막는다.
- 비밀번호 칸을 조건 없이 허용한다: 에이전트가 값을 지어내 실제 사이트에 가입·로그인을 시도할 수 있다.
- 심각도 높음만 검출로 센다: 중간 등급인 R06·R10 정답을 놓친 것으로 세게 된다.
- 참고 목록까지 검출로 센다: 리포트에서 문제로 보여 주지 않는 것을 맞혔다고 세게 된다.
- R을 예상 소요 시간에 넣는다: 같은 버전을 다시 재도 값이 달라져 전후 비교에 쓸 수 없다.
- 서버 응답만 있는 경우를 위해 `effect_type`에 값을 더한다: 동결 스키마·DB·화면 타입을 모두 바꿔야 한다.
- 과업 조회를 더하지 않는다: 리포트 제목이 "과업 #번호"로 남고, 측정 목록 화면이 최근에 잰 과업만 찾을 수 있다.
- `POST /human-sessions`를 만든다: 비교 계산에 필요하지 않고, 참가자 자료가 스테이징 서버에 한 벌 더 생긴다.
- 수집 스크립트에서 속성 변경을 빼 `stable`을 줄인다: 본 수집 직전에 수집 코드를 바꾸면 6페이지 확인을 다시 해야 하고(`human-study/session-procedure.md`), 파일럿 자료와 기준이 달라진다. 속성만 바뀌어 열리는 메뉴의 화면 변화도 놓친다.
- 재생이 끊긴 지점부터 에이전트 1회로 이어 간다: 시도가 1회라 중앙값과 편차가 없어 전후 비교 판정에 쓸 수 없다. 재생 구간과 에이전트 구간이 섞인 기록의 지표 계산도 새로 정해야 한다.
