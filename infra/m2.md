# W2 M2 로컬 실행 환경

기준 main: `2bb2eb5` (PR #28까지), 2026-11-06 KST.
이 문서는 로컬 Compose·CI 담당 범위다. API·에이전트 제품 구현은 각 담당자가 제공한다.

## 확인된 외부 의존성

2026-11-06 GitHub의 원격 19개 브랜치 파일 트리와 최근 PR을 확인했다.
API 서버 Python 모듈, `worker/agent/run.py`, PlaywrightDriver 구현은 어느 브랜치에도 없었다.
열린 PR은 없고, 관련 열린 이슈는 #26(M2 에이전트 루프↔큐 연결)이다.
따라서 현재 인프라 연결 검사와 실제 API→큐→워커→리포트 E2E는 구분한다.
(11/8 PR #32로 API 서버 들어옴)

## 서비스 구성

| 서비스 | 용도 |
|---|---|
| api (`m2` 프로필) | 백엔드 실행 명령을 `STEPMETER_API_COMMAND`로 받아 실행. 미설정이면 명확한 오류로 종료 |
| worker (`m2`) | `JOB_FUNC`가 import 가능할 때만 RQ `runs` 큐를 소비 |
| m2-fixtures (`m2`) | 고정 signup 페이지를 `http://m2-fixtures:8765/`에서 제공 |
| migrate (`tools`, `m2`) | DB 준비 후 Alembic 실행. API·worker는 마이그레이션 성공 후 시작 |
| test-db, test-redis (`test`) | 개발 DB·Redis와 분리된 자동 테스트 전용 서비스 |

API는 호스트의 127.0.0.1:8000으로만 공개하며 `API_PORT`로 포트를 바꿀 수 있다.
테스트 페이지는 내부 네트워크에서만 접근한다. 컨테이너 안의 localhost는 호스트가 아니므로
M2 요청의 project.base_url에는 `http://m2-fixtures:8765/signup/index.html`을 사용한다.
호스트에서 E2E를 실행하더라도 이 URL은 테스트 프로세스가 아니라 워커가 방문한다.

API·worker는 `screenshots` 볼륨을 `/app/data/screenshots`에 공유한다.
기존 save_screenshot(bytes)의 상대 경로와 일치한다. 이미지가 디렉터리를 비특권 사용자 소유로 준비한다.
API 응답의 스크린샷 제공·서명 기능 자체는 백엔드가 구현해야 한다.

## 지금 실행 가능한 검사

```sh
docker compose --profile m2 config --quiet
docker compose --profile test --profile m2 build tests worker
docker compose --profile test run --rm tests
docker compose --profile m2 run --rm worker python -m infra.scripts.check_m2_network
```

마지막 명령은 실제 워커와 같은 네트워크·환경·볼륨으로 DB SELECT 1, Redis PING,
가짜 답 목록 로드, Chromium에서 signup 페이지 수집→입력→신청→done.html,
스크린샷 저장을 확인한다. API/에이전트 루프나 metric 저장을 대신하지 않는다.
`run`의 command override로 검사만 수행하며 실제 큐 작업은 소비하지 않는다.
`tests`는 테스트 전용 DB/Redis를 비우는 기존 테스트들을 실행하므로 개발 서비스에 연결하지 않는다.

## 담당 구현이 main에 들어온 뒤

1. 백엔드 담당자가 API 실행 명령·추가 의존성·초대 코드 발급 명령을 제공한다.
   이미지 의존성은 기존 requirements-dev.txt에 포함돼야 한다. 부팅 중 pip 설치는 하지 않는다.
   API는 컨테이너 안의 0.0.0.0:8000에서 수신해야 한다.
2. 에이전트 코어가 큐의 `JOB_FUNC=worker.agent.run.run`을 제공한다(#26).
3. `.env`에 제공받은 `STEPMETER_API_COMMAND`를 설정하고 이미지를 재빌드한다.
   예시 실행 명령을 임의로 가정하지 않았다. 키·초대 코드는 .env.example에 넣지 않는다.
4. 서비스를 실행한다.

```sh
docker compose --profile m2 up -d --build --wait api worker
```

API healthcheck는 포트가 열리는지만 확인한다. 엔드포인트·인증·리포트 정상 여부는 아래 E2E로 확인한다.
worker는 모듈이 없는 상태에서 큐를 소비하지 않고 오류로 종료한다.
로컬 M2 worker는 fake 모드로 고정돼 있어 유료 LLM 키를 전달하지 않는다.
STAGING/운영용 설정으로 사용하지 않는다.

5. 초대 코드 발급 후 호스트에서 E2E를 실행한다.

```sh
export STEPMETER_API_URL=http://127.0.0.1:8000
export STEPMETER_E2E_SITE_URL=http://m2-fixtures:8765/
# STEPMETER_ACCESS_CODE는 발급한 값을 환경 변수로 설정
python -m unittest tests.e2e.test_m2_flow -v
```

테스트가 자동으로 띄우는 localhost 사이트를 쓰면 Docker 워커에서 접근할 수 없으므로 SITE_URL은 반드시 지정한다.
이 테스트는 새 프로젝트·과업·run을 생성한다. 테스트 DB를 초기화하는 전체 unittest를 개발 DB에 연결하지 않는다.
같은 버전에서 취소→step 이후 정리·완료 상태를 덮어쓰지 않는지도 실제 코어 구현과 함께 검증해야 한다.

종료: `docker compose --profile m2 --profile test down` (볼륨을 지우는 `-v` 사용하지 않음).

## CI

- Python job: Redis 7 서비스를 제공하고 TEST_REDIS_URL=redis://localhost:6379/15를 설정한다.
- Docker job: 전용 test-redis와 연결해 큐 테스트를 실행한다. M2 컨테이너 네트워크 검사도 수행한다.
- 실제 M2 API E2E는 구현이 없어 아직 실행할 수 없다. CI 성공을 M2 합격으로 간주하지 않는다.
- 테스트 페이지·API 키·초대 코드 없는 fake 모드만 사용하고 홀드아웃 평가를 실행하지 않는다.
