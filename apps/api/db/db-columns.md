# StepMeter DB 칸(column) 설명

> 기준: 개발계획서 v1.1 §10 데이터 모델(16개 테이블) + 기능 구현을 위해 추가하기로 한 칸 10개.
> - **🆕 추가** 표시가 붙은 칸은 계획서 §10에는 없고, 우리가 추가하기로 한 칸이다. 마이그레이션(Alembic)에서 새로 만들어야 한다.
> - **[추정]**: 계획서에 직접 적혀 있지 않아 문맥으로 채운 설명이다. 확정 전에 담당과 맞춰야 한다.
> - 근거 칸은 "~기능을 구현하기 위해 ~과정을 거쳐 / ~값을 전달받아 ~테이블에 저장해야 한다" 형식으로 쓰고, 끝에 계획서 절 번호(§)를 붙였다.
> - 모든 테이블의 `id`는 그 행(row)을 가리키는 고유 번호(기본 키)다. 다른 테이블의 `id`를 가리키는 `xxx_id`는 연결 칸(외래 키)이다.

## project — 측정 대상 사이트 하나

| 칸 | 담는 정보 | 근거 |
|---|---|---|
| id | 프로젝트 번호 | 프로젝트 생성 기능을 구현하기 위해 POST /projects 요청을 받아 새 행을 만들고, 그 번호를 응답으로 돌려줘야 한다. 이후 과업·측정이 모두 이 번호로 묶인다. (§11) |
| name | 사용자가 붙인 프로젝트 이름 | 프로젝트 목록 화면을 구현하기 위해 POST /projects의 요청 본문에서 이름을 전달받아 project에 저장하고, GET /projects에서 돌려줘야 한다. (§11) |
| base_url | 측정할 사이트의 기본 주소 | 측정 기능을 구현하기 위해 사용자가 입력한 사이트 주소를 전달받아 project에 저장하고, 워커가 측정을 시작할 때 큐 페이로드에 담아 넘겨 브라우저가 이 주소를 열게 해야 한다. [추정: 과업마다 시작 주소가 다를 수 있는지는 미정] (§2.2) |
| owner_id | 프로젝트를 만든 사람 | 프로젝트를 사람(또는 팀)별로 나누는 기능을 구현하기 위해, 요청 헤더의 초대 코드(X-Access-Code)를 확인해 어떤 access_code인지 찾은 뒤 그 번호를 project에 저장해야 한다. [추정: 로그인 기능이 없어서 access_code.id를 가리킬 가능성이 크다. PM 미결 "초대 코드별 프로젝트 분리"에 따라 바뀐다] (§11 F17) |
| created_at | 프로젝트를 만든 시각 | 프로젝트 목록을 최신순으로 보여주기 위해 생성 요청을 받은 순간 서버 시각을 project에 저장해야 한다. (§10) |
| daily_run_limit | 하루에 만들 수 있는 측정 수 (기본 10) | 일일 측정 상한(F17)을 구현하기 위해, 측정 요청이 올 때마다 이 프로젝트에서 오늘 만든 run 수(replay_only 제외)를 세어 이 값과 비교하고, 넘으면 429를 돌려줘야 한다. 프로젝트마다 다르게 둘 수 있게 project에 저장한다. (§11) |

## task — 프로젝트 안의 과업 하나 ("회원가입하기" 같은 목표)

| 칸 | 담는 정보 | 근거 |
|---|---|---|
| project_id | 소속 프로젝트 | 과업 생성 기능을 구현하기 위해 POST /projects/{id}/tasks 경로의 {id}를 전달받아 task에 저장해야 한다. (§11) |
| description | 에이전트에게 주는 과업 설명 문장 | 에이전트가 무엇을 해야 하는지 알게 하기 위해, 사용자가 입력한 과업 설명을 전달받아 task에 저장하고, 측정할 때 큐 페이로드에 담아 워커의 프롬프트로 넘겨야 한다. (§2.2, §4.4) |
| success_condition (JSONB) | 성공 판정 조건 (URL 포함, 특정 텍스트 등장 등) | 과업 성공 판정을 구현하기 위해, 사용자가 정한 조건을 전달받아 task에 저장하고, 워커가 에이전트의 done 뒤에 이 조건으로 성공 여부를 확인하게 해야 한다. 조건이 비어 있으면 LLM이 마지막 화면으로 판정하고 "추정"으로 표시한다. (§4.5) |
| credentials_ref | 로그인이 필요한 과업의 계정 정보 위치(참조값) | 로그인 뒤에만 할 수 있는 과업을 측정하기 위해, 계정 정보는 암호화 저장소에 따로 두고 그 위치만 task에 저장해야 한다. 비밀번호 자체를 DB에 넣지 않기 위해서다. 암호화 저장소가 아직 정해지지 않아 M3 뒤로 미뤘다. (§10 비고) |

- [ ] `credentials_ref`의 암호화 저장소 정하기 (M3 뒤로 미룸)
- [ ] 과업 수정 API를 만들 때: 기준 run 이후 과업이 바뀌었는지 알 방법 추가 (`task.updated_at` 또는 run에 과업 버전 저장). §7.2-5 "과업이 바뀌면 재생 안 함" 때문

## run — 측정 요청 1건 (사용자가 "측정" 버튼을 한 번 누른 것)

| 칸 | 담는 정보 | 근거 |
|---|---|---|
| task_id | 측정한 과업 | 측정 요청 기능을 구현하기 위해 POST /tasks/{id}/runs 경로의 {id}를 전달받아 run에 저장해야 한다. 측정 이력(GET /tasks/{id}/runs)도 이 칸으로 찾는다. (§11) |
| viewport | 화면 종류: desktop(1280×800) / mobile(390×844) | 데스크톱·모바일 측정을 구현하기 위해 측정 요청 본문에서 viewport를 전달받아 run에 저장하고, 큐 페이로드로 워커에 넘겨 브라우저 크기를 정하게 해야 한다. 비교할 때도 같은 viewport끼리만 비교한다. (§4.2, §7.1) |
| mode | 측정 방식. **auto** = 이전 측정의 대표 경로를 LLM 없이 먼저 재생하고, 끊기면 그 지점부터 에이전트가 이어서 수행(기본값, 재측정에 적합) / **agent** = 재생 없이 처음부터 LLM 에이전트로 repeat_n회 실행(첫 측정, 과업이 바뀐 경우) / **replay_only** = 재생만 하고 끊기면 거기서 멈춤. LLM 비용이 거의 없어 CI용이며 일일 상한에 세지 않음 | 재측정 비용을 줄이는 재생 기능을 구현하기 위해, 측정 요청 본문에서 mode를 전달받아 run에 저장해야 한다. 워커는 이 값을 보고 재생을 먼저 할지 정하고, API는 replay_only를 일일 상한 계산에서 뺀다. (§11, §7.2) |
| base_run_id | 비교·재생 기준이 되는 이전 run | 재측정 비교를 구현하기 위해, 같은 (과업, viewport)의 직전 측정을 찾거나 사용자가 고른 기준 측정 번호를 전달받아 run에 저장해야 한다. 워커는 이 run의 대표 경로를 재생한다. 첫 측정이면 비어 있다. (§7.1, §7.2) |
| repeat_n | 에이전트 반복 실행 횟수 (기본 3, 고급 5) | 에이전트 편차를 줄이는 반복 실행을 구현하기 위해, 측정 요청 본문에서 repeat_n을 전달받아 run에 저장하고, 큐가 이 수만큼 병렬 실행(최대 3개 동시)을 나눠 돌리게 해야 한다. (§4.6) |
| model | 사용한 LLM 모델 이름 | 모델별 비용·성능 비교를 구현하기 위해, 측정 요청 본문에서 모델 이름을 전달받아 run에 저장하고 워커의 LLM 어댑터에 넘겨야 한다. (§3, §11) |
| prompt_version | 사용한 프롬프트 버전 | 결과 재현과 프롬프트 개선 효과 비교를 구현하기 위해, 워커가 측정에 쓴 prompts/ 파일 버전을 전달받아 run에 저장해야 한다. (§4.4, §9.3) |
| status | queued / running / completed / failed / canceled | 진행 상황 화면을 구현하기 위해, API가 run을 만들 때 queued로 저장하고, 워커가 작업을 꺼낼 때 running, 끝날 때 completed로 바꿔야 한다. 에이전트 실패나 사이트 차단은 completed + attempt.end_reason으로 표현하고, failed는 서비스 장애에만 쓴다. 취소 요청(POST /runs/{id}/cancel)을 받으면 canceled로 바꾼다. (§2.2) |
| progress | 진행률 0~100 정수 | 대시보드의 진행률 표시(2초 폴링)를 구현하기 위해, 워커가 단계를 끝낼 때마다 진행 정도를 계산해 run에 갱신하고, GET /runs/{id}가 이 값을 돌려줘야 한다. 계산식(예: 끝난 단계 수 ÷ (repeat_n × 30))은 아직 미정. (§2.2) |
| cost_usd | 이 측정에 든 LLM 비용 합계(달러) | 예산 상한·알림을 구현하기 위해, 이 run에 속한 llm_call의 cost_usd를 모두 더해 run에 저장해야 한다. 그래야 측정 1건 비용을 바로 보여주고 하루·월 합계를 빠르게 셀 수 있다. [추정: 합산 시점(측정 끝날 때 vs 호출마다)은 미정] (§16, §13) |
| started_at | 워커가 시작한 시각 | 측정에 걸린 시간을 보여주기 위해, 워커가 큐에서 작업을 꺼낸 순간의 시각을 run에 저장해야 한다. 대기 중(queued)이면 비어 있다. (§2.2) |
| finished_at | 끝난 시각 (완료·실패·취소 모두) | 측정 소요 시간 계산과 이력 화면을 구현하기 위해, run 상태가 completed·failed·canceled로 바뀌는 순간의 시각을 저장해야 한다. (§2.2) |
| 🆕 **created_at** | 측정 요청을 받은 시각 | 일일 측정 상한(F17)을 구현하기 위해, API가 측정 요청을 받는 순간의 시각을 run에 저장하고, 새 요청이 올 때 "같은 프로젝트에서 오늘(KST 자정 기준) created_at인 run 수"를 세야 한다. started_at은 대기 중에는 비어 있어서 이 계산에 쓸 수 없다. 측정 이력(F11)도 이 칸으로 정렬한다. (§11) |
| 🆕 **representative_attempt_id** | 재생에 쓸 대표 경로 attempt | 경로 고정 재생을 구현하기 위해, 측정이 끝난 뒤 성공한 실행 중 경로 의존 지표가 중앙값에 가장 가까운 attempt를 골라 그 번호를 run에 저장해야 한다. 다음 측정은 base_run_id → representative_attempt_id → 그 attempt의 step 순서로 따라가 행동을 재생한다. (§7.2-1, W3) |

**처리할 일**
- [ ] `status` 경계 규칙 정하기: 워커가 잡아서 기록할 수 있는 오류는 `attempt.end_reason = error`, 워커 자체가 죽거나 저장 실패면 `run.status = failed` (W2 큐·워커 연결 때)
- [ ] queued에 너무 오래 머문 run을 failed로 바꾸는 시간 초과 기준 정하기
- [ ] `progress` 계산식 정하기 (예: 끝난 단계 수 ÷ (repeat_n × 30))
- [ ] `cost_usd` 합산 시점 정하기 (호출마다 vs 측정 끝날 때)
- [ ] `representative_attempt_id`: 성공한 실행이 없으면 null로 두고, 그 run을 기준으로 한 auto 측정은 에이전트로 돌게 처리
- [ ] `mode` 기본값 auto는 openapi.yaml RunCreate에서 확정됨 — 확인만

## attempt — run 안의 실행 1회 (반복 실행 한 번 또는 재생 한 번)

| 칸 | 담는 정보 | 근거 |
|---|---|---|
| run_id | 소속 run | 반복 실행을 구현하기 위해, 워커가 run 하나를 repeat_n개의 실행으로 나눌 때 각 실행에 어떤 run 소속인지 저장해야 한다. (§4.6) |
| index | run 안에서 몇 번째 실행인지 | 단계 상세 화면을 구현하기 위해, GET /runs/{id}/attempts/{n}의 n으로 실행을 찾을 수 있게 워커가 실행 순번을 attempt에 저장해야 한다. (§11) |
| kind | replay / agent | 재생 비교와 에이전트 비교를 구분하기 위해, 워커가 이 실행이 재생인지 에이전트인지 attempt에 저장해야 한다. 비교 판정 기준(§7.4 표)이 둘이 다르다. (§7.2, §7.4) |
| replay_status | full / partial (재생일 때만) | 재생 완주율 평가와 비교 화면을 구현하기 위해, 워커가 재생을 끝까지 했는지(full), 중간에 끊겼는지(partial) attempt에 저장해야 한다. (§7.2, §8.2) |
| diverged_at_step | 재생이 끊긴 단계 번호 | "경로가 바뀐 지점" 표시와 재생 확인 화면을 구현하기 위해, 워커가 매칭에 실패하거나 사후 검증에 실패한 단계 번호를 attempt에 저장해야 한다. 이 지점에서 사용자에게 "이전의 [가입 완료]가 이 버튼인가요?"를 묻는다. (§7.2-4) |
| end_reason | 성공 / 포기 / 반복 루프 / 예산 초과 / 차단 / 오류 | 리포트의 실패 분류를 구현하기 위해, 워커가 실행이 끝난 이유를 §4.5 표의 값 중 하나로 attempt에 저장해야 한다. 반복 루프면 R05 이슈도 만든다. (§4.5) |
| success | 과업 성공 여부 | 과업 성공률과 "3회 중 2회 이상 성공" 판정을 구현하기 위해, 워커가 성공 조건 충족 여부를 attempt에 저장해야 한다. 2회 미만이면 경로 의존 지표를 비교에 쓰지 않는다. (§4.6, §7.4) |
| steps_count | 실행한 단계 수 | 단계 수 지표와 예산 초과(30단계) 판정을 구현하기 위해, 워커가 실행한 행동 수를 attempt에 저장해야 한다. (§4.5, §5.6) |
| 🆕 **end_detail** | 끝난 이유의 세부 내용 (포기 이유 문장, 오류 메시지, 차단 원인) | 리포트의 "실패 + 에이전트가 적은 이유", "측정 불가 + 오류 메시지" 표시를 구현하기 위해, 워커가 에이전트의 fail 이유나 오류 메시지를 전달받아 attempt에 저장해야 한다. end_reason은 종류만 담아서 이 문장을 담을 곳이 없다. (§4.5) |
